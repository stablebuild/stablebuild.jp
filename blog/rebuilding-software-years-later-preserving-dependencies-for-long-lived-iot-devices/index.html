数年後も IoT ソフトウェアを再ビルドするために：長期運用を支える依存関係の保持

IoT デバイスは、そのソフトウェアを開発した環境が変わった後も、長く使われ続けることがあります。

工場に設置されたゲートウェイ、建物内のセンサー、現場で稼働する組み込みコントローラー。こうした機器は、最初のリリースから何年も経った後に、保守が必要になる場合があります。セキュリティ上の脆弱性が見つかったり、顧客から不具合の報告があったりすれば、エンジニアは機器上で動作するソフトウェアを再ビルドしなければなりません。

ソースコードは Git に残っていても、ビルドに使ったコンパイラ、OS パッケージ、SDK などは、すでに変わっていたり、取得できなくなっていたりする可能性があります。

長期運用する IoT デバイスを保守するチームには、サポート期間を通じて、ソフトウェアを再ビルドし、更新できる状態を維持するという課題があります。その基盤となるのが、確実な依存関係の保持です。

時間が経つほど、IoT ソフトウェアの再ビルドが難しくなる理由

一般的なソフトウェアでは、要件の変化に合わせて新しいプラットフォームやインフラへ移行できる場合があります。一方、組み込み機器では、変更できる範囲が限られます。

デバイスは、何年も前に選定したプロセッサーアーキテクチャ、OS、ハードウェアインターフェースを使い続けているかもしれません。ファームウェアも、特定のコンパイラ、ボードサポートパッケージ（BSP）、メーカー提供のライブラリに依存している場合があります。

これらを置き換えることは、必ずしも簡単ではありません。新しい SDK では対象のハードウェアがサポートされていないことがあります。コンパイラの更新によって生成されるバイナリが変わったり、古いコードが前提としていた条件が成り立たなくなったりする可能性もあります。必要な依存関係が、元のダウンロード先から削除されていることもあります。

こうした問題が表面化する場面の一つが、ファームウェアの再ビルドです。

たとえば、産業用監視機器を保守するチームを考えてみます。元のファームウェアは2022年に開発され、機器は2026年も稼働しています。顧客から不具合が報告され、小さな修正が必要になりました。チームは元のソースコードを取得し、該当リリースのタグをチェックアウトして、再ビルドを試みます。

ところが、必要な依存関係を取得できず、ビルドが失敗します。チームは、顧客の問題を修正することに加え、当時の開発環境を再構築しなければなりません。報告された不具合の修正よりも、元のビルド環境の復旧に時間がかかる可能性があります。

ソースコードだけでは、ファームウェアを再現できない

Git リポジトリには、ソースコードやビルド設定を保存できます。しかし、ビルド中に外部からダウンロードするものまで、自動で保存されるわけではありません。

組み込みソフトウェアのビルドでは、通常、次のようなものが必要になります。

ビルドに必要なもの 数年後の再ビルドで問題になり得る点
クロスコンパイル用ツールチェーン コンパイラのバージョンによって、生成されるバイナリが変わる場合がある
ボードサポートパッケージ（BSP） ハードウェア固有のファイルが、特定のプラットフォームのバージョンでしか動作しない場合がある
OS パッケージ 必要なバージョンが置き換えられたり、削除されたりする
コンテナイメージ タグが指す内容が変わったり、イメージが削除されたりする
メーカー提供の SDK 古いリリースの配布が終了する場合がある
ダウンロードするアーカイブ 外部 URL が変わったり、利用できなくなったりする
Python 製のビルドツール パッケージ本体や間接的な依存関係のバージョンが変わる場合がある

この様な組み込みソフトウェアの依存関係は、アプリケーションのリポジトリに保存されていなくても、ビルド環境の一部です。

組み込み Linux のビルド環境を用意する、次の簡略化した Dockerfile を見てみます。

FROM ubuntu:22.04

RUN apt-get update && \
    apt-get install -y \
    build-essential \
    gcc-arm-none-eabi \
    make

この Dockerfile では、Ubuntu のリリースと、ビルドに必要なパッケージを指定しています。しかし、各パッケージの正確なバージョンまでは固定していません。

数年後に同じ Dockerfile を実行すると、リポジトリから別のバージョンが取得される可能性があります。ubuntu:22.04 が指すベースイメージの内容も、変わっているかもしれません。

ソースコードを変更していなくても、コンパイルに使う環境が当時と一致するとは限りません。組み込みソフトウェアの再現可能なビルドを実現するには、こうした外部から取得するものも管理する必要があります。

古い依存関係が取得できなくなると、何が起きるのか

パッケージのバージョンを正確に指定していても、古いビルドが失敗することはあります。

バージョンの固定は、パッケージマネージャーに「どのバージョンを取得するか」を伝えます。そのパッケージが、配布元のリポジトリに残り続けることを保証するものではありません。

数年前に公開された特定のツールチェーンが必要でも、そのパッケージが削除されていれば、元の取得先からはダウンロードできません。同じ問題は、Docker イメージ、Python パッケージ、メーカー提供の SDK でも起こり得ます。

小さな修正だけが必要な場合には、特に負担になります。ビルドできる環境を整えるためだけに、複数の依存関係を更新しなければならなくなるからです。その更新によって、本来の修正とは関係のない変更が入り、新しいファームウェアが意図どおりに動作するかを確認しにくくなります。

SDK のバージョン固定やパッケージのバージョン記録は有用ですが、それだけでは十分ではありません。必要なファイルを、引き続き取得できることも重要です。

Docker イメージだけでは解決できない理由

コンテナは、開発環境をまとめて管理するために役立ちます。コンパイラ、ビルドツール、システムライブラリを含むイメージを作り、複数の開発者や CI システムで共通して使えば、ローカル環境とビルドサーバーの違いを減らせます。

ただし、Docker イメージのタグが指す内容は、固定されているとは限りません。同じタグに別のイメージが割り当てられることもあれば、配布元のレジストリから取得できなくなることもあります。

特定のダイジェストで内容を指定したり、取得済みの内容を保持するミラーを利用したりすれば、コンテナ環境をより正確に管理できます。ただし、ダイジェストによる指定と、イメージ自体の保持は別です。イミュータブルな Docker イメージを使う場合も、必要な内容を取得できる状態にしておく必要があります。

さらに、ビルド中に取得する依存関係も残ります。Docker のビルドでは、APT で OS パッケージを取得したり、pip で Python 製のツールをインストールしたり、外部 URL から SDK をダウンロードしたりすることがあります。

ベースイメージが同じでも、これらの追加ダウンロードによって環境が変わる可能性があります。過去のビルド環境を維持するには、コンテナイメージと、その内部で取得する依存関係の両方を管理する必要があります。

組み込み Linux や Yocto を使うプロジェクトでも起こる問題

この課題は、Docker を使う開発環境に限りません。

多くの組み込み機器では、Yocto Project などのツールで構築した独自の Linux ディストリビューションを使用しています。Yocto を使うビルドは、ソースリポジトリ、リリースのアーカイブ、パッチファイル、メタデータ、ビルドツールなどに依存します。

Yocto Project には、ソースファイルをダウンロードしてキャッシュする仕組みがあります。BitBake も、PREMIRRORS や MIRRORS などの設定変数を通じて、取得元として優先するミラーや、代替のミラーを指定できます。

これらの仕組みは、必要なファイルをどこから取得するかの管理に役立ちます。ただし、過去のビルドを支えるために使うなら、ローカルキャッシュや外部のミラー自体も維持しなければなりません。

長期的な組み込み Linux のビルドで重要なのは、再び必要になったときに、当時のファイルを取得できるかどうかです。ビルドシステムに正しいリビジョンが記録されていても、アクセス可能なコピーがなければ、失われたファイルは取得できません。

過去の依存関係を維持することも、製品の長期サポートの一部になります。

過去の状態を保持するパッケージミラーの役割

一般的なパッケージミラーは、ソフトウェアパッケージの代替の取得先を提供します。ダウンロード速度や可用性の向上に役立つ一方、配布元のリポジトリの変更に追従する場合があります。

過去の状態を保持するパッケージミラーは、以前の時点に対応するリポジトリの内容やパッケージを保存します。これにより、古いビルドを作成した当時のパッケージを、後から取得できるようにします。

たとえば、ある組み込み Linux アプリケーションが、特定の Ubuntu パッケージの組み合わせでビルドされていたとします。後からその環境を再構築する際に、現在の配布元が提供するパッケージに頼るのではなく、保存された当時のリポジトリの状態を参照できます。

不足する依存関係を補うために無関係なパッケージ更新を取り込まずに、過去のリリースを調査できるようになります。

ただし、こうしたミラーが担うのは、外部の依存関係を引き続き取得できるようにする部分です。最終的なビルド結果には、コンパイラの設定、タイムスタンプ、ビルド時のパス、ハードウェア固有の動作なども影響します。

StableBuild による長期的な依存関係の保持

StableBuild は、取得した内容を変更せず保持するミラーや、過去の状態を参照できるミラーを提供します。

対応する取得対象には、Docker イメージ、Ubuntu・Debian・Alpine の OS パッケージ、Python パッケージ、外部 URL からダウンロードするファイルがあります。

組み込みソフトウェアは、OS パッケージ、コンテナ、ツールチェーン、外部で配布されるファイルなどを組み合わせて利用することが多いため、こうした機能は IoT 開発にも関わります。

StableBuild の Docker ミラーは、サービス経由で取得したイメージを保持します。配布元のイメージが変更・削除されても、保存済みの内容を取得できるようにする仕組みです。OS パッケージのミラーでは、過去のリポジトリのスナップショットを保持し、特定の日付に対応する取得元を指定できます。その他のビルド用ファイルについても、外部 URL から取得した内容の保持をファイルミラーで支援します。

チームが依存関係の種類ごとに保存用の基盤を構築・運用する代わりに、既存のパッケージ管理やコンテナの運用に組み込めます。開発者は Docker、APT、APK、pip などの使い慣れたツールを使いながら、対応する依存関係の取得先を StableBuild に設定します。

古い組み込みソフトウェアを保守するチームにとって、これは過去のリリースを再ビルドする際の不確実性を減らすことにつながります。

ただし、依存関係は、まだ取得できるうちに保持する必要があります。保存する前に失われたファイルを、ミラーが必ず復元できるわけではありません。

StableBuild は、ビルドの再現性向上を推進する Reproducible Builds プロジェクトの「Success Stories」と「Involved Projects」の両ページに掲載されました。これは、過去のビルド環境を再現する際に必要な外部依存関係を利用できる状態に保つという、StableBuild の取り組みを示すものです。

デバイスを出荷する前から、保守に備える

長期的にビルドできる状態は、出荷から何年も経った後よりも、出荷前の方が整えやすくなります。外部の依存関係もリリース記録の一部として扱うことで、将来の保守に備えられます。

  • ビルド環境を記録する
    ソースコードのリビジョン、コンパイラのバージョン、SDK のリリース、コンテナイメージのダイジェスト、対象アーキテクチャ、依存パッケージを記録します。
  • 外部から取得するファイルを保持する
    必要なコンテナイメージ、パッケージ、ツールチェーンのアーカイブなどを、適切な長期保存やミラーの仕組みで取得できる状態にします。
  • 過去のリリースを定期的に再ビルドする
    記録した構成を使って以前のファームウェアを再ビルドし、緊急の保守依頼が来る前に、不足している依存関係を把握します。
  • 保守のための修正と、依存関係の更新を分けて検証する
    元の環境を保持しておくと、不具合の修正を、無関係な更新と切り分けて評価しやすくなります。
  • セキュリティ更新の手順を用意する
    古い環境を保持することは、脆弱性を含むソフトウェアを本番環境で使い続けることではありません。修正の評価、依存関係の更新、更新後のファームウェアの検証を進める手順が必要です。

これらの取り組みは、初期開発だけでなく、デバイスの運用期間を通じた保守を支えます。

IoT ソフトウェアの更新を支えるために

稼働中のデバイスをサポートするには、最初のファームウェアを作るだけでは十分ではありません。初回リリースから長い時間が経った後も、脆弱性の調査、古いハードウェアとの互換性の維持、IoT ソフトウェアの更新が必要になる場合があります。

米国国立標準技術研究所（NIST）も、ソフトウェア更新機能やメーカーによる継続的な支援を含め、IoT 製品のライフサイクル全体でサイバーセキュリティを計画することを重視しています。

過去のビルドを再現できることは、こうした保守作業に役立ちます。更新後に問題が発生した場合は、過去の既知の環境と比較できます。特定の依存関係に脆弱性が見つかった場合は、その依存関係を使っていたリリースを特定し、適切な修正を検討できます。

保存された依存関係は、当時のビルドに必要なものを取得できるようにすることで、これらの調査を支えます。産業設備、商業施設、遠隔地などで使われ、最新のプラットフォームへ簡単に置き換えられない製品では、保守にかかる負担の軽減につながります。

出荷時だけでなく、運用期間を通じて保守できる状態へ

ファームウェアのリリースは、IoT 製品のソフトウェアライフサイクルの始まりです。

何年も経った後に、更新、不具合調査、過去のリリースの再ビルドが必要になることがあります。そのとき、元のコンパイラ、パッケージ、SDK などを取得できることは、ソースコードを参照できることと同じくらい重要です。

必要なものが失われる前に保持しておけば、長期的な保守に備えられます。StableBuild は、対応する外部依存関係を、過去の状態や取得時の内容を保持するミラーで保存し、その管理を支援します。

何年も保守し続けるデバイスでは、将来も依存関係を取得できるかどうかを、開発当初から計画に含める必要があります。

長期的な組み込みソフトウェアの保守に役立つ機能については、StableBuild の機能紹介をご覧ください。
