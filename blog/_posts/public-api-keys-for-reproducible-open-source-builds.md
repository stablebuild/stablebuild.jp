デフォルトでは、StableBuild の API キーは非公開です。プライベートなビルドではそれで問題ありませんが、オープンソースプロジェクトではすぐに扱いづらくなります。

Dockerfile やビルド設定を公開していても、リポジトリをクローンした人が StableBuild 経由で同じバージョンに固定されたパッケージ、キャッシュ済みのコンテナ、その他の依存関係を利用するには、依然として認証情報が必要です。

[パブリック API キー](https://stablebuild.gitbook.io/ja/product/public-api-keys)は、プロジェクトと一緒に公開することを前提にしています。キーをリポジトリにコミットし、ビルドが StableBuild 経由で要求する依存関係を記録しておけば、誰でも同じ依存関係を取得できます。一方で、組織の StableBuild キャッシュにある他の依存関係まで取得できるわけではありません。

## **プロジェクトに必要な依存関係を記録する**

パブリック API キーは、最初は読み取り専用です。キーの許可リストに登録され、すでに StableBuild にキャッシュされている依存関係だけを提供できます。

その許可リストを作るには、一時的にキーの書き込みウィンドウを開き、ビルドを一度実行します。

書き込みウィンドウが開いている間、そのキーは通常の StableBuild API キーと同じように動作します。そのビルド中に StableBuild 経由で要求された依存関係は、すべてパブリック API キーの許可リストに追加されます。

ビルドが終わったら、再び書き込みウィンドウを閉じます。

それ以降、そのパブリック API キーを使う人は記録済みの依存関係を取得できますが、StableBuild アカウント経由で任意の新しいパッケージ、コンテナ、ファイルを取得することはできません。

StableBuild は Dockerfile を解析したり、プロジェクトの依存関係グラフを推測したりしません。書き込みウィンドウが開いている間に、ビルドが実際に StableBuild 経由で要求したものだけを記録します。

## **1つのキーでビルド全体をカバーできる**

同じパブリック API キーを StableBuild の複数のミラーで利用できます。

たとえば、Dockerfile でベースイメージ、Debian パッケージ、Python の依存関係、URL からダウンロードするファイルに StableBuild を使う場合は、次のようになります。

```dockerfile
FROM your-prefix-pub-myproject.dockermirror.stablebuild.com/python:3.12-slim

ARG SB_API_KEY=your-prefix-pub-myproject
ARG APT_PIN_DATE=2026-09-29T08:40:01Z

COPY ./sb-apt.sh /opt/sb-apt.sh
RUN bash /opt/sb-apt.sh load-apt-sources debian
RUN apt update && apt install -y curl

RUN pip install \
    -i https://your-prefix-pub-myproject.pypimirror.stablebuild.com/2026-09-01/ \
    requests==2.32.3

RUN curl -O \
    "https://your-prefix-pub-myproject.httpcache.stablebuild.com/my-cache-key/https://bootstrap.pypa.io/get-pip.py"
```

書き込みウィンドウを開いた状態でビルドを実行すると、これらの StableBuild サービスを通じて要求された依存関係が、そのキーに記録されます。

ウィンドウを閉じると、パブリック API キーから取得できるのは記録済みの依存関係だけになります。

そのため、リポジトリをクローンした人は、メンテナーから非公開の StableBuild API キーを受け取らなくても同じビルドを実行できます。プロジェクトとは関係のないその他のキャッシュ済み依存関係は、引き続き非公開のままです。

## **許可リストを更新する**

依存関係の構成はいずれ変わります。

プロジェクトを更新してビルドに新しい依存関係が必要になったら、もう一度書き込みウィンドウを開き、更新後のビルドを実行してから閉じます。StableBuild 経由で新たに要求された依存関係が、そのキーに追加されます。

StableBuild のダッシュボードから許可リストを確認し、パブリック API キー経由で提供する必要がなくなった項目を個別に削除することもできます。

書き込みウィンドウは、1時間、24時間、7日後に自動で閉じるよう設定できます。ただし、ビルドが終わったらできるだけ早く閉じることをおすすめします。ウィンドウが開いている間は、パブリック API キーを知っている人なら誰でも、そのキーを使って新しい依存関係を取得できるためです。

## **再現可能なビルドには、取得できる入力が必要**

[Reproducible Builds プロジェクト](https://reproducible-builds.org/docs/definition/)では、同じソースコード、ビルド環境、ビルド手順から、ビット単位で同一の成果物を再生成できることを、再現可能なビルドと定義しています。また、ビルド環境に関係する要素には通常、依存関係とそのバージョンも含まれるとしています。

オープンソースプロジェクトでは、再ビルドする人がそうした入力を実際に取得できることも重要です。

Dockerfile でパッケージのバージョンを固定したり、特定のコンテナを指定したりすることはできます。しかし、公開されたビルド設定が非公開の API キーを使って StableBuild を参照している場合、コントリビューターがその依存関係を取得するには依然として認証情報が必要です。

StableBuild のパブリック API キーを使えば、そのアクセス情報をビルド設定と一緒にプロジェクトに含められます。コントリビューターや下流の利用者は、組織の非公開 StableBuild API キーや、その他のキャッシュ済み依存関係へのアクセス権を渡されることなく、そのプロジェクト用に記録された依存関係を取得できます。

パブリック API キーだけで、ビルド結果が完全に再現可能になるわけではありません。ビルド結果は、タイムスタンプ、環境の違い、StableBuild の外にあるさまざまな要素にも影響されます。パブリック API キーが解決するのは、もっと限定された問題です。StableBuild で保持した依存関係を、そのプロジェクトを再ビルドしたい人も取得できるようにします。

## **パブリック API キーも自分のアカウントに紐づく**

パブリック API キー経由のトラフィックは、そのキーを作成した組織の利用量として計上されます。

Community プランでは、パブリック API キーを使ったビルドも組織の既存の月間トラフィック枠を使用し、通常の月間トラフィック上限が適用されます。

トラフィックは **Billing > Raw usage logs** で確認できます。各リクエストには、どの API キーが使われたかも表示されます。

そのため、プロジェクトと一緒に公開したパブリック API キーが、公開後にどのように使われているかも確認できます。

オープンソースプロジェクトを管理していて、コントリビューターにも同じバージョンに固定された依存関係を使ってビルドしてほしい場合は、[StableBuild アカウントを作成](https://stablebuild.jp/pricing/)し、パブリック API キーを追加して、書き込みウィンドウを開いた状態でビルドを実行すれば、プロジェクトの依存関係を記録できます。

詳しい設定手順は、[パブリック API キーのドキュメント](https://stablebuild.gitbook.io/ja/product/public-api-keys)を参照してください。
